# Yuki Desktop 消息全链路动画衔接任务书

日期：2026-11-12

状态：用户在本机使用 #62 版本后说「消息的发送接收全链路动画衔接都很不自然，请你全部检查优化一下」。本任务书即执行依据，基线为 #63（`feat/liquid-morph`）。

## 1. 目标与原则

一条消息从送出到收到回复，画面里的每样东西都沿同一根弹簧连续移动，没有任何一帧的跳动。

- 禁止防御性编程：沿用已有的弹簧（`Spring`、`sampleSpring`、`springs.bubble`），不引入动画库；不改消息、回执与查證的事实流程。
- 列表滚动、气泡升起、被挤开的元素用同一根弹簧，起点终点按事实位置计算，不按经验时长拼接。
- 用户自己滚动（滚轮、触控、键盘、拖动滚动条）立即接管，动画让位。
- 「减少动态效果」时一切立即到位，与现在一致。

## 2. 调研基线与确认的问题

方法：真实 Electron + 真实后端（模型延迟 2 秒），记录 DOM 与滚动的逐帧事件并截屏（`scratchpad/flow/log-before.txt`）。从点送出起计：

| 时刻 | 事件 | 问题 |
| --- | --- | --- |
| 375ms | 待确认气泡出现，升起动画 783ms | 同一帧 `scrollTop` 0→106 瞬间跳：旧消息一下蹦上去，新气泡还在慢慢升 |
| 495ms | 「送出中」→「已接收」 | 文字硬切 |
| 626ms | 「正在處理」出现，无动画 | 高度 +48，`scrollTop` 106→154 瞬间跳，正值气泡升起途中 |
| 2972ms | Yuki 回复出现并长出 | `scrollTop` 154→236 瞬间跳 82px，回复边长边被整体拽上去；回复插在提示上方，提示被瞬间挤下 |
| 5096ms | 「正在處理」消失（回合结束才消失，属事实） | 无动画，高度 −48，`scrollTop` 236→188 瞬间回跳 |

原因：`Conversation.tsx` 在送出时 `log.scrollTop = log.scrollHeight`，其余变化在下一帧 `scrollTo({ top: scrollHeight })`，都是瞬间到底；处理提示直接挂载、卸载；状态文字直接替换。

## 3. 施工项

### F1 弹簧滑动的列表（`motion/glide.ts`）
`glide(list, top)`：以 `springs.bubble` 的实时弹簧把 `scrollTop` 推向目标；进行中再次调用只改目标、保留速度；滚轮、触控、按键、在列表上按下指针立即停止。滑动期间的滚动事件不改写「是否在底部」。

### F2 送出：旧消息与新气泡同一根弹簧
送出时不再先跳到底：气泡在当前滚动位置量出起点（可向上平移，不再限制为非负），列表同时以同一弹簧滑到底。两者叠加后，气泡视觉位置正好是从输入框到最终位置的弹簧插值。

### F3 其余高度变化都滑动
回复到达、提示出现与消失、回执改变高度时，若在底部，列表滑到底；「减少动态效果」时立即到底。

### F4 被挤开的元素跟着滑
每次提交后记录列表内消息与提示的位置；某元素未新增却因上方插入而位移，就从旧位置以同一弹簧滑到新位置。

### F5 「正在處理」进场与退场
进场与 Yuki 的回复同一种生长；退场时高度、间距与不透明度以不过冲的弹簧收起后再卸载，期间若重新开始处理则取消退场。

### F6 状态文字交替
「送出中」「已接收」「已取得原回執」等更换时新文字淡入并轻微上移。

## 4. 失败情形（先写，再写代码）

E2E `tests/e2e/message-flow.spec.ts`（`conversation-glass` 回归页，按真实时间逐帧采样），产物 `message-flow.json`。

1. 送出到回复整段，任一帧 `scrollTop` 变化超过 40px，或超过当次总位移的 40%。
2. 送出时任一帧旧消息（上一条消息）的位置变化超过 40px。
3. 送出时气泡第一帧不在输入框范围内，或最后不在其静止位置（±1px）。
4. 「正在處理」出现时没有生长动画，或任一帧位置跳动超过 40px。
5. 回复插入时「正在處理」任一帧位置跳动超过 40px。
6. 「正在處理」消失时高度没有经过至少 5 帧逐步收起，或收起期间列表跳动超过 40px。
7. 状态文字更换后新文字没有进场动画。
8. 滑动途中用滚轮向上滚，或程序滚动（跳到某条消息、页内查找），列表之后仍被拉回底部，或「是否在底部」仍为真。
9. 「减少动态效果」时出现任何滑动或形变动画，或送出后列表没有立即到底。

## 随施工调整的既有测试与发现

- `renderer-regressions`「delayed image decode preserves the actual tail position」：该夹具在释放图片时同时送来一条更晚的消息（1025），按 F3 应以弹簧滑到底；原断言要求两帧内即到底，改为等待到底，仍断言不出现「↓ 新訊息」。
- 施工中发现并修正一个既有竞争：程序把列表放到底部后、滚动事件送达前内容又长高，滚动处理按新高度判为「离开底部」，此后不再跟随（打开对话时可停在离底 48–92px 处）。现在程序放置的位置会被记下，滚动事件发现位置正是程序放置的就不改写「是否在底部」；行的尺寸变化（`ResizeObserver` 观察列表与各行）在底部时立即贴底。
- 只有同一对话中出现更晚的消息才算「到来」而滑动；打开对话、图片解码、版面稳定都立即贴底，不播放滚动动画。

## CI 发现与修正

`workspace-acceptance`（Linux、Windows）超时：截图步骤以 `scrollIntoView` 把标题放到中间，而当时一段滑到末端的动画仍在进行——弹簧的静止判定沿用 0–1 进度值的阈值（0.0005），用在像素上过严，末端又有 1px 级抖动，滑动迟迟不停；它把位置拉回末端，那次滚动事件也因「正在滑动」被当成应用自己的而不更新「是否在底部」。修正：以 0.5px、20px/s 判定到位；每帧若列表不在上一帧放置的位置即视为他人滚动而停止；「应用自己移动」只以位置恰为上次放置值判断。
